# 로또 6/45 조합 분석

**https://ch-bry.github.io/lotto-analysis/**


당첨 확률은 어떤 조합을 고르든 **8,145,060분의 1로 완전히 같습니다.** 이 저장소는 그것을
바꾸려 하지 않습니다. 대신 실제로 바꿀 수 있는 두 가지를 데이터로 최적화합니다.

1. **당첨 시 수령액** — 1~3등은 파리뮤추얼이라 당첨금 풀을 당첨자끼리 나눕니다.
   남들이 덜 고르는 조합을 택하면 당첨됐을 때 나눌 사람이 줄어듭니다.
2. **최소 1개 이상 당첨 확률** — 여러 장을 살 때 티켓끼리 번호를 덜 겹치게 짜면
   "전부 꽝"이 될 확률이 줄어듭니다. 기대 당첨 개수는 그대로입니다.

기대수익률은 어떤 방법으로도 약 **-50%** 입니다. 로또는 판매액의 절반만 당첨금으로
돌려주는 구조이고, 이 저장소도 그것을 바꾸지 못합니다.

## 핵심 아이디어

5등(3개 매칭) 당첨자는 회차당 약 160만 명이라 순수한 확률 오차가 **0.08%** 밖에 안 되는데,
실제 관측 편차는 **4.4%** 입니다(54배). 이 편차는 잡음이 아니라 **플레이어의 번호 선호**입니다.
여기서 45개 번호 각각의 인기 가중치와 조합 단위 선호를 추정할 수 있습니다.

매칭 개수별로 내재 편차를 뽑아보면:

| 매칭 | 3개 | 4개 | 5개 | 6개(정확) |
|---|---|---|---|---|
| 내재 인기 편차 (SD) | 0.104 | 0.125 | 0.157 | **0.286** |

번호별 선호만 존재한다면 네 값이 같아야 합니다. 단조 증가한다는 것은 **조합 단위 선호가
따로 존재한다**는 직접 증거입니다.

## 검증 결과

인기도 모델은 **4·5등 당첨자 수만으로 학습**하고 **1등은 전혀 쓰지 않았습니다.**
1000회까지만 학습한 뒤 1001~1238회(238개 회차)에서 검증한 결과:

| 모델이 예측한 인기도 | 실제 1등 당첨자 ÷ 기대치 |
|---|---|
| 최저 25% (비인기) | **0.909** |
| 2분위 | 0.883 |
| 3분위 | 1.027 |
| 최고 25% (인기) | **1.200** |

상관계수 r = +0.301, 순열검정 p = 0.00015.
실제 지급된 1등 1인당 당첨금은 비인기 절반 **25.3억원** vs 인기 절반 **20.2억원** (1.25배).

포트폴리오 성능은 가능한 추첨 8,145,060가지를 **전수 열거**해 계산했습니다(표본오차 0):

| | P(1등) | P(1개↑ 당첨) | 평균 당첨수 | 인기 배수 |
|---|---|---|---|---|
| 10장 자동선택 | 0.000001228 | 0.21997 | 0.23834 | 0.989 |
| 10장 최적화 | **0.000001228** (동일) | **0.23008** | 0.23834 (동일) | **0.807** |
| 20장 자동선택 | 0.000002455 | 0.37858 | 0.47668 | 0.993 |
| 20장 최적화 | **0.000002455** (동일) | **0.42556** | 0.47668 (동일) | **0.861** |

한편 "핫넘버", "콜드넘버", "궁합수", "직전 회차 번호 제외" 등 **번호 예측 가설 30개는
전부 기각**됐습니다(FDR 보정 후 생존 0개). 그 결과도 사이트에 그대로 공개합니다.

## 구조

```
scripts/
  fetch.py        데이터 수집 (smok95/lotto 미러, 증분)
  features.py     조합 특징 추출 (전부 벡터화, 8백만 조합 스코어링 가능)
  hypotheses.py   Group A — 통념 30개 몬테카를로 검정 + BH FDR 보정
  popularity.py   Group B — 번호/조합 인기도 모델 (등수별 민감도 가중 회귀)
  portfolio.py    Group C — 저인기 + 커버리지 최적화, 전수 열거 평가
  backtest.py     워크포워드 백테스트, 거짓양성 통제 검증
  build.py        전체 파이프라인 -> web/data/*.json
web/              정적 사이트 (빌드 산출물만 읽음)
.github/workflows/weekly.yml   매주 일요일 00:30 KST 자동 재분석 + Pages 배포
```

## 실행

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python scripts/build.py          # 수집 + 전체 분석 + web/data 생성
.venv/bin/python -m http.server 8080 --directory web
```

개발 중 빠른 확인은 `--quick`(축소 시뮬레이션), 재수집 생략은 `--skip-fetch`.

개별 스크립트를 직접 실행하면 각 단계의 진단 출력을 볼 수 있습니다.

```bash
.venv/bin/python scripts/popularity.py     # 홀드아웃 검증 + 번호별 인기도
.venv/bin/python scripts/hypotheses.py     # 가설 검정표
.venv/bin/python scripts/portfolio.py      # 전수 열거 포트폴리오 비교
```

## 무인 운영

데이터 원본인 [smok95/lotto](https://github.com/smok95/lotto)는 매주 토요일 추첨 직후
21시경 봇이 자동 갱신하며 CORS가 열려 있습니다. 그래서 두 겹으로 최신 상태를 유지합니다.

- **GitHub Actions** — 일요일 00:30 KST cron 이 신규 회차를 받아 전체 재분석 후 Pages 배포.
- **브라우저 폴백** — 페이지 로드 시 미러에서 최신 회차를 확인하고, 사전 계산 데이터보다
  새 회차가 있으면 `web/js/generator.js`가 브라우저에서 추천을 다시 만듭니다.
  Actions 가 실패해도 최신 회차가 반영됩니다.
